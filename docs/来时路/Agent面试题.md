# [Agent面试题](https://xiaolinnote.com/ai/agent/agent_info.html)
## Agent是什么，与LLM的本质不同是什么
### 简要回答
Agent本质上是 **自主**完成目标 的AI系统，与传统AI最核心的区别是 「**自主性**」和 「**能行动**」。

传统AI是一问一答，每次都是独立的、被动响应的；而Agent有自己的规划能力，给他一个复杂目标，它会自己完成任务拆解，通过调工具、访问记忆、感知环境来一步步执行，直到完成。

不只是输出文字，而是真的能做事。

### 详细解析
#### 普通LLM的局限性
普通LLM即使多轮对话也只能根据当前上下文被动响应，普通LLM最直观的问题是「**知识被冻结**」，在这之上更本质的问题是它「**不能行动**」，对于“查资料后整理成报告”这种任务，它也无法完成，因为「**没有持续状态**」。

这三个局限就造成：知识是死的、手脚是没有的、记忆是断的，结合在一起就成了LLM只能一问一答，复杂多步骤的协作任务无法完成。

#### Agent的独特之处
Agent的核心运行闭环是：感知 -> 规划 -> 行动 -> 再感知。

比如给Agent一个任务“帮我调研竞品然后整理成报告”，他不是输出一段文字结束，而是先拆解任务：搜索哪些关键词、访问哪些网站、怎么组织内容，然后按步骤执行，每一步的结果又反馈回来，指导下一步怎么做。

这种能力核心是三件事：工具调用、记忆机制、推理与纠错
1. 工具调用（Tool Use）：让Agent从只会说话到能做事的关键。Agent能调用外部工具，使用工具这个过程不是LLM自己执行的，而是LLM告诉系统「该调什么工具」，代码去真正执行，结果再反馈给LLM。LLM只是大脑不是手脚。
```txt
工具的注册就好像技能说明书，只是告诉LLM「有什么能力，需要什么参数」，LLM通过这个说明书自己决定该调什么工具、参数填什么，然后把决策结果通过JSON告诉系统，真正执行的还是代码，「决策与执行分离」是工具调用最核心的一点。
```
2. 记忆机制（memory）：传统LLM每次对话都是「失忆」的，除非手动传入上下文，否则LLM记不住上一次输入输出了什么。Agent系统通常设计 **短期记忆** 和 **长期记忆** 两层。短期记忆就是当前任务执行过程中的中间状态（前几步的结果），长期记忆则是跨任务的（用户偏好、历史操作记录），通常用向量数据库来存储，需要的时候做语义检索取出。
3. 多步推理与自我纠错（Reasoning）：这是Agent区别于简单自动化脚本的关键。Agent在执行过程中如果有失败，不会崩溃而是能够感知失败、分析原因、换方式重试。

#### Agent生态
Agent越来越多，它们怎么协作？工具越来越多，怎么统一管理？这两个问题催生出来两个非常重要的标准协议。
1. MCP：Model Context Protocol，模型上下文协议。它就是Agent工具世界的USB-C接口。MCP的做法是定义一套标准的JSON-RPC协议，工具提供方只要这个标准暴露能力（变成一个MCP Server），任何支持MCP的Agent（内置MCP Server）都能发现和调用这个工具，不需要额外写适配代码。
```txt
MCP架构分为3层：
- Host：最外层（用户直接交互的AI应用，比如Codex、Cursor等）
- Client：中间层（负责与MCP Server建立连接、管理通信）
- Server：最内层（真正暴露工具能力的服务）
```

2. A2A：Agent to Agent，Agent间通信协议。MCP解决的是「Agent如何调用工具」，A2A解决的是「Agent怎么与另一个Agent协作」。A2A的核心设计理念是Agent Card，每个Agent都有一张“名片”，记录了一个Agent能做什么、在做什么、需要输入什么，其他Agent读取后明白该如何与他协作。

MCP负责Agent与工具间的连接，A2A负责Agent与Agent间的通信。

### 总结
Agent与LLM的区别主要三件事：
- Agent有自主规划能力，它能拆解复杂任务。
- Agent能行动，通过工具调用与外部世界交互。
- Agent有闭环，每步的结果反馈回来指导下一步，而不是一次性完成就结束。

## Agent的基本架构由哪些核心组件构成
### 简要回答
Agent的基本架构有四个核心组件：LLM、工具、记忆、规划模块。
- LLM：系统的大脑，负责理解任务和做决策
- 工具：让Agent能够与外部世界交互
- 记忆：让Agent在任务执行过程中保持状态，不会失忆
- 规划模块：负责把复杂目标拆解成可执行的步骤

### 详细解析
#### LLM核心
它是整个Agent的大脑，所有的输入不管是用户的命令、工具返回的结果、记忆中的内容，最终都要经过LLM来理解和决策。

还有一个容易被忽略的重要东西：「**System Prompt**」（系统提示词），在Agent开始工作之前，System Prompt就定义好了他的角色、行为边界、输出格式等。实际工程中，System Prompt的调优往往占了开发时间的相当大一部分，因为它是能最直接控制Agent行为的手段。

另一个实际工程中非常重要的问题是：选哪个「**模型**」？常见的工程做法是：用推理能力强的大模型做核心决策「任务规划、关键判断」，用更快更便宜的小模型做简单任务「意图分类、格式提取」，根据不同环节的需求来搭配。

其次是「**工具调用的稳定性**」问题，有些模型生成的JSON格式经常出错、参数乱填，导致工具调用失败，这在生产环境会带来大量的重试和token浪费。

最后是「**上下文窗口大小**」，Agent每一步的工具返回结果都会塞进上下文，如果模型的上下文窗口太小，后面的步骤就不知道前面发生了什么。

模型大致可以分为三类：
- 推理模型：DeepSeek-v4、ChatGPT-6、Kimi K3
- 通用大模型：Claude Sonnet、Claude Opus、ChatGPT-6、Gemini Pro
- 小模型：Claude Haiku、ChatGPT-mini、Gemini Flash

#### 工具系统
工具系统是Agent和外部世界交互的唯一入口。LLM本身是纯粹的语言处理器，不能读文件、不能执行代码，这些限制都可以通过工具突破。任何能用函数封装的能力都可以变成工具。

在工具的定义中，没有一行执行逻辑代码，它是一个关于「名字、描述、参数」描述的JSON格式，工具描述的质量直接影响Agent的表现。LLM是根据工具的描述来判断什么时候该用这个工具的。

随着工具越来越多，管理和标准化就成了问题，于是又了MCP。

#### 记忆系统
记忆系统分为 **短期记忆** 和 **长期记忆**。

- 短期记忆：就是当前本轮对话的上下文，装在context window中。Agent在一次任务执行中靠它记住中间状态。
```txt
短期记忆最大的问题是上下文窗口有限，上下文快满时，要么做「摘要压缩」要么做「滑动窗口」。
```
- 长期记忆：通常用向量数据库来实现，重要信息embedding之后存起来，下次用的时候做语义检索拿回来。长期记忆的组织形式如下：
  - 语义记忆：存事实性知识
  - 情景记忆：存具体的经历
  - 程序性记忆：存工作经验
```txt
长期记忆的挑战在于「什么该存什么不该存」以及「存了之后怎么清理」。如果存的太多，检索出的噪声过多反而影响LLM决策；如果存的太少，又失去了长期记忆的意义。目前较好的工程实践是在存之前先做一轮重要性评估，只把真正有价值的信息持久化。还有一个做法是「记忆衰减」，做法是给每条记忆加一个时间权重，越久远的权重越低，检索时优先返回权重高的记忆。

记忆衰减通常用一个指数衰减公式：记忆的相关性分数 = 语义相似度 x 时间衰减因子，时间衰减因子随时间推移逐渐降低，衰减速度可以根据业务场景调整。
```

#### 规划模块
规划模块决定了Agent能不能应对复杂任务。规划模块的底层依赖LLM的推理能力，而提升推理能力有几种主要的技术手段：
- CoT（Chain of Thought，思维链）：最基础，核心思想是让模型把思考过程写出来，而不是直接输出最终答案，主要是通过prompt设计来实现。
- ToT（Tree of Thoughts，思维树）：在CoT的基础上进一步提升，不再走一条线性的推理链，而是在每个推理节点上展开多个可能的分支，然后评估每个分支的质量，选出最优的分支继续往下走。

CoT是一路走到底，ToT是在岔路口先选择最好的那条路再往下走。ToT在需要创造性思考或复杂决策的场景下效果更好，但是计算成本更高因为要评估多条路径。

规划模块在实际运作中有两种主流模式：
- Plan-and-Execute模式：先规划后执行。先让LLM输出一个完整的步骤列表，然后按顺序逐步执行。
  - 优点：整体结构清晰，执行前可以看到完整计划，方便人工审核
  - 缺点：如果中间某个环节结果不符合预期，原来的计划就可能失效，需要重新规划
- ReAct模式：边执行边规划。每走一步就根据当前结果来重新思考下一步该做什么，不提前制定完整计划。
  - 优点：灵活性极高，根据实际情况随时调整。
  - 缺点：容易跑偏，每一步都是局部最优，但是会忽略整体目标。

### 总结
Agent基本架构主要是由LLM、工具系统、记忆系统、规划模块这四个组件组成。
- 工具系统要注意LLM本身不执行工具，LLM只是决定使用什么工具，真正执行的还是代码，决策和执行分离。
- 记忆系统分为两层，短期记忆用context window，长期记忆用向量数据库。
- 规划模块是Agent拆解复杂任务的关键。

## Tools、Workflow、Agent的概念与区别
### 简要回答
这三个概念是粒度从小到大的三层结构：
- Tools：最小的能力单元，是封装好的可调用函数，只负责执行，没有决策能力。
- Agent：完整的决策系统，内部用LLM做大脑，自己判断什么时候调用Tools、什么时候结束，是主动的。
- Workflow：更上层编排框架，把Agent、LLM、Tools组织成一条确定性流程，每个节点做什么、按什么顺序流转，是开发者实现写死的。

三者的核心区别是：Tools不做决策只执行，Agent自己做决策，Workflow是开发者把所有节点的决策提前写好。

### 详细解析
这三者不是同一维度的东西，而是力度不同、可以相互嵌套的三层结构。
#### Tools
Tools是整个体系中最简单、最基本的概念，本质上是按特定格式暴露给LLM的函数，Tool是给LLM调用的，所以必须给它配一份LLM能看懂的Schema描述，除去Schema外，它和普通函数没有本质区别。

Tools本身没有决策能力，它不知道自己应该在何时被使用，Tools的使命是把一个具体能力封装好，随时待命等待被Agent调用。

一个好的Tool设计有几个核心原则：
- 职责单一：确保一个工具只做一件事。
- 描述要准确：description是Agent能够理解Tool功能的唯一途径。
- 错误信息要清晰：工具执行失败时，返回的错误信息应是LLM能理解的格式。

Tools的管理与发现基于Anthropic提出的MCP。

#### Agent
Agent就是「拿着工具，决定自己做什么」的角色。Agent与Tools的本质是：Tools被动等待被调用，Agent主动做决策。

Agent本质是一个循环机制，但与普通代码不一样的地方在于，普通代码的每一步都是开发者预先写好的，而Agent的执行路径是由LLM实时决定的。但既然停止条件是由LLM自己决策，难免遇到陷入死循环的情况，所以可以设计四种停止条件：
- LLM主动盘点停止：这是最理想的情况
- 设置最大循环次数：超过设置的次数无论是否完成都强制停止，返回当前已有结果
- 设置总执行时间上限：超时机制
- 设置Token预算上限：防止成本失控

Agent的另一个副作用是「不确定性」，LLM本质上是一个概率模型，每次生成都有随机性。灵活性和不确定性是一对孪生兄弟，Agent的灵活也伴随着不可预测。所以生产环境中，往往会给Agent加上详细的执行日志，记录每一步的思考过程和工具调用结果，方便事后追溯。

#### Workflow
Workflow把整个执行流程的骨架都写进代码中，LLM、Agent、Tools都只是这个流程中的节点，每个节点完成自己的那一步，整体走哪条路、下一步怎么走，全由开发者的代码决定。

Workflow最大的优点是可预测、可控、好调试，生产环境中出问题，可以通过打断点来定位故障。

#### 三者组合
Agentic Workflow才是生产主流。在真实项目中，三者通常是同事存在、相互嵌套的：
- 完全靠Agent自主决策的系统：行为难以控制，出现问题难以排查，成本也容易失控
- 完全靠Workflow写死的系统：一般没办法穷举所有情况到代码中，遇到预料之外的输入容易导致失败或输出很差的结果。
- Agentic Workflow：用Workflow固定的骨架，在需要灵活判断的节点嵌入Agent，其余固定节点直接用LLM或Tools。骨架是确定的，开发者可以控制整体行为，便于调试；关键节点是灵活的，Agent应对复杂情况。

Anthropic在Agent工程实践中总结的常见的Workflow编排模式：
- Prompt Chaining提示链：将大任务分解为小任务，前一步的输出作为下一步的输入
- Routing路由：先用LLM做分类判断，然后根据分类结果把请求分发到不同的处理分支
- Parallelization并行化：把可以同时进行的子任务并行执行，最后汇总结果，在多维度分析的场景下特别适用。
- Orchestrator-Workers编排者-工人：一个中央编排者负责分配任务，多个worker各自完成子任务，适合任务可以分解但是子任务之间相互独立的场景。
- Evaluator-Optimizer评估者-优化者：LLM负责生成输出，由另一个LLM负责评估这个输出的质量，如果评估不通过就把反馈给回生成者。本质是用LLM来充当审核人。评估标准要在代码里定义清楚（比如写一个打分函数），不能让评估者自由发挥。

实际项目中这几个模式会混合使用，根据具体需求组合出最合适的架构。

## Agent设计范式，Agent与Workflow的区别是什么
### 简要回答
Agent常见的设计范式有：Plan-and-Execute、ReAct、Reflection等。

Agent和Workflow的核心区别是「谁来决定下一步」，Workflow是开发者把流程提前写死，Agent是由LLM自己决定下一步做什么。实际工程中是对两者混用，固定流程部分用Workflow，灵活决策的节点嵌入Agent能力。保证整体可控的同时局部也有灵活性。

### 详细解析
#### Agent的三种主流设计范式
1. ReAct（Reasoning + Acting）：推理Reasoning和行动Acting交替进行，具体来说，ReAct的每轮循环由三个步骤组成，形成了Thought-Action-Observation循环。
  - Thought阶段：LLM先把当前情况分析一遍，把推理过程写出来。
  - Action阶段：LLM根据思考的结论决定调用哪个工具、传什么参数。
  - Observation阶段：工具返回的结果反馈到LLM，LLM读取结果，进入下一轮的Thought阶段，重新分析局面决定接下来怎么做。
```txt
将这三步显式分开，是因为如果让LLM直接输出行动，LLM经常会冲动决策。添加Thought环节，LLM先把问题梳理清楚，记录推理过程，决策质量就稳定多了。而且Thought内容可见，出了问题方便调试。这个循环会不断重复，直到LLM在某轮Thought中判断可以输出结果。

ReAct的明显短板是，每一步都采用局部最优策略，处理复杂的需要全局规划的任务时容易在中间环节偏离目标。
```
2. Plan-and-Execute：针对ReAct的短板，Plan-and-Execute则先让LLM来规划并输出完整的步骤列表，再根据步骤规则执行。
```txt
规划和执行解耦的好处是，复杂任务的整体结构变得清晰，可以在执行前人工审核计划是否合理。

Plan-and-Execute的一个关键机制是「动态重规划」，成熟的Plan-and-Execute实现中，每执行一步都会把结果反馈给规划器，规划器判断后续步骤是否需要调整，甚至插入新的步骤来应对。缺点是增加了规划和重规划环节对LLM的调用，延迟和成本都会增加。而且如果初始规划方向本身就是错误的，那后续调整也都无法挽回。
```
3. Reflection：在前两种的基础上加了一层质量保障。做法是在Agent完成一步或者整个任务后，在让另一个LLM判断结果是否符合预期。如果评估不通过就重试或者换策略，这个机制能显著提高输出质量。
```txt
Reflection的变体是Reflexion。与Reflection的区别在于，Reflexion不止是评估结果是否符合预期，还会生成具体的反思总结，记录失败原因和改进建议，然后把总结作为额外上下文传给下一次尝试。代价也很直接，每多一轮Reflection就多一次甚至多次LLM调用，成本和延迟都会增加。
```

三种范式怎么选，需要评估「任务复杂度」和「质量要求」：
- 任务步骤不多，每步相对独立：ReAct
- 任务复杂，步骤间依赖关系需全局统筹：Plan-and-Execute
- 对输出质量要求高，允许多花时间和成本：在前两者基础上叠加Reflection

三者不是互斥的，真实项目中会混合使用：Plan-and-Execute做整体规划，每个步骤内部用ReAct来执行，关键步骤加上Reflection来保证质量。

**Anthropic在工程博客中总结**：能用Workflow解决的问题，就不要用Agent。 
```txt
在生产环境中，可控性比灵活性更重要。
```

## Agent推理模式有哪些
### 简要回答
Agent推理模式最基础的就是直接输出答案，没有中间推理；CoT是让LLM先把推理过程写出来再给答案；ReAct是在CoT基础上增加了行动环节，让LLM交替进行输出思考和工具调用，每次行动后再根据结果继续思考，形成循环。

ReAct是目前Agent用的最广的模式，因为推理过程可见，又能动态利用外部工具。

### 详细解析
#### 推理模式
通过不同的方式，让LLM把隐式的思考过程呈现出来，减少多步推理中的累积误差。

#### CoT
全称Chain of Thought，思维链，核心想法很朴素：在 prompt 里加一句「让我们一步步思考」，LLM 就会先把推理步骤写出来，再给答案，而不是直接蹦出结论。本质是因为 LLM 的输出是顺序生成的，先写出来的推理内容会进入上下文，成为后续生成的依据。

CoT有两种触发方式：
1. Zero-shot CoT：做法非常简单，直接在 prompt 末尾加上「让我们一步步思考」这句话就行了，LLM 会自己展开推理过程，不需要你提供任何示例。这种方式的优势是零成本、即插即用，缺点是 LLM 的推理格式和深度完全靠它自己发挥，不太稳定，有时候会写得很详细，有时候又跳步。
2. Few-shot Cot：需要在 prompt 里给几个带有完整推理过程的例子，让 LLM 照着这个格式来模仿。Few-shot 的效果更稳定，特别适合输出格式要求比较固定的场景，代价是需要你提前准备高质量的示例，而且示例本身也会占用 token。

CoT的根本局限是：它是纯文本推理，无法和外部世界交互。整个过程再完整也拿不到实时数据，不能执行计算不能访问数据库，只能根据训练时的数据来推理。

我们需要的不是一个能把推理写出来的LLM，而是一个能在推理过程中「向外取数据」、「调用工具」、「回来继续推理」，且这些事时原生设计的系统，于是有了ReAct。

#### ReAct
ReAct全称Reasoning and Acting，核心思路是在CoT的推理链里插入真实的「行动」。让LLM按「思考-行动-观察」循环推进任务，先思考该怎么做，然后调用一个工具去获取信息或执行操作，把工具返回的结果作为新的「观察」接收回来，然后进入下一轮思考，直到LLM判断任务完成。

为什么不用纯CoT或Act-only？
- 纯CoT只能在文本内推理，推理结果再完美也拿不到真实数据，对于需要实时信息的场景无能为力，纯靠内部推理容易产生幻觉，因为没有外部事实来校验。
- Act-only是让LLM直接输出工具调用序列，不写思考过程，问题在于每一步行动之间没有推理链条衔接，遇到需要调整策略的情况容易出错。在HotpotQA这类多跳问答基准测试中，Act-only的准确率明显低于CoT和ReAct。

ReAct的精妙之处是把推理和行动结合在一起：Thought帮助LLM分析局势、决定下一步做什么，Action把决策落地为真实操作，Observation把外部世界的反馈带回LLM，形成闭环。推理为行动提供方向，行动为推理提供事实。

ReAct的实现原理是通过prompt格式来约束LLM的输出结构，但循环不是LLM自己执行的，而是代码在外部驱动的。LLM 每次只做一件事：根据当前的历史，输出下一步的 Thought 加上 Action。代码负责检测它的输出，判断「有没有 Final Answer」，如果没有就解析出 Action、执行对应的工具、把工具结果作为 Observation 填回历史，再次调用 LLM，一轮一轮地转。整个loop里真正的智能在LLM每次输出的Thought结果中，它在分析当前情况、做出下一步决策；代码框架则是管理对话历史、执行工具、检测循环终止条件。

靠prompt格式约束加文本解析来驱动工具调用是ReAct的经典实现，现代LLM已原生支持Function Calling/Tool Calling，模型可以直接输出结构化的 JSON 工具调用，不再需要解析文本来提取工具调用信息，ReAct的实现也更简单了。

ReAct并不完美，实际项目中存在两个坑：
- 循环漂移：由于ReAct每一步都是根据当前历史重新决策的，没有全局计划的约束，运行中可能偏离最初目标。
- 错误传播：ReAct的每一步决策都在前面步骤的结果之上，如果中间步骤拿到错误信息或工具返回错误结果，后面的推理就会被带偏。

而且ReAct 没有内置的「回头检查」机制，它不会停下来反问自己「前面那步的结果靠谱吗」，而是默认前面的 Observation 都是对的，一路往前冲。一旦错误出现在早期步骤，整条推理链后面全部白费。这两个问题的根源本质都是：ReAct是纯粹的「前向推理」，没有全局规划和反思机制。解决这个问题最直接的思路就是：让LLM先以全局视角把整个任务弄清楚，列出完整执行计划，再一步一步执行，这就是Plan-and-Execute。

#### Plan-and-Execute
Plan-and-Execute把整个任务流程拆成两个明确的阶段：
- 规划Planner：把用户的任务目标交给 LLM，让它先不急着动手，而是站在全局的角度想清楚。
- 执行Executor：拿着规划好的计划，按顺序一步一步地执行。

#### ReAct与Plan-and-Execute的适用场景
ReAct的优势在于灵活，每一步都能根据最新情况做决策，特别适合那些任务边界不太明确、需要探索性地获取信息的场景，比如开放式的问答、信息搜索这类任务。代价是容易偏移，且每一步都要把完整历史传给LLM，步骤较多时token消耗会线性增长。

Plan-and-Execute的优势在于有全局视野，不容易跑偏，特别适合那些目标明确、需要多步骤协作完成的复杂任务，比如深度研究、长文写作、多工具协同的数据分析。它的代价是初始规划本身就需要一次 LLM 调用，如果任务很简单（一两步就能搞定），这个规划步骤反而是多余的开销。

实际工程中二者通常是结合使用，常见的做法是：用Plan-and-Execute做全局规划，用ReAct做每一步的执行。规划阶段可以用更强大的推理大模型保证质量，执行阶段用便宜的小模型来跑具体的工具调用，这样既保证了全局方向不跑偏又控制了成本。

## ReAct、Plan-and-Execute、Reflection的核心区别
### 简要回答
这三者是Agent开发中最主流的三种设计范式，核心区别在于「决策和执行的关系」：

- ReAct是边想边干，走一步看一步，单步迭代实时调整，灵活度最高
- Plan-and-Execute是先想全再干，制定完整计划再分步执行，适合长流程复杂任务，不容易跑偏
- Reflection不是独立的完整流程，而是给前两者添加「检查修正」，用来提升输出质量

实际选型需要考虑三个维度：任务复杂度、流程确定性、输出质量要求：
- 入门首选ReAct
- 复杂任务用Plan-and-Execute
- 高要求场景添加Reflection

### 设计范式和推理模式
- 设计范式：搭建Agent的「顶层执行流程框架」
- 推理模式：Agent在执行每一步时的「思考方式」

设计模式好比公司的管理制度，推理模式是员工的干活方式。

### ReAct：单步迭代范式
ReAct是Agent范式的祖宗，本质是「思考-行动-观察-再思考」的循环。

ReAct与另外两者的区别在于，它没有提前做完整规划的环节，规划和执行混在一起，边执行边思考；Plan-and-Execute则是先完整规划再统一执行；与Reflection相比，ReAct的循环中没有专门的自我检查环节，只有行动后根据结果进行观察。

ReAct最大的优势是实现简单、灵活度高、逻辑透明，出错时好排查，入门简单。但是对于长流程、多步骤的复杂任务，容易在执行中跑偏，偏离最初目标；也容易在某一步陷入无效循环。它更适合流程不固定、复杂度适中的任务

### Plan-and-Execute：规划执行范式
Plan-and-Execute 是针对 ReAct「长任务容易跑偏」的痛点，做的针对性优化，ReAct 是「走一步看一步，边想边干」；Plan-and-Execute 是「先把完整计划定好，再按计划一步步干」，完全是两种做事思路。

Plan-and-Execute与ReAct的核心区别是把「规划」和「行动」完全解耦了，先有完整的执行计划，再分步执行，全程不会偏离最初的目标，而不是像 ReAct 那样边规划边执行、随时可能调整方向。和 Reflection 相比，它的核心是「先规划再执行」，没有强制的自我检查环节，但两者可以叠加使用。

Plan-and-Execute整体结构清晰、执行链路可控、复杂度高的长流程任务不容易跑偏，识别出无依赖的步骤后可以并行执行，大幅度降低整体耗时。代价是灵活度不如ReAct，遇到计划外的情况容易卡住，实现也更复杂，需要分别维护规划模块和执行模块，token消耗也会增加。适合流程长、复杂度高的任务。

### Reflection：反思迭代范式
Reflection不是单独的设计范式，而是给ReAct和Plan-and-Execute添加的一个「自我检查」环节。它的核心循环是在原本的范式基础上，添加「生成-评估-改进」闭环，专门设置独立的检查环节，判断当前的输出有没有问题、达不达标，不达标就重试或调整策略，直到符合要求为止。

ReAct和Plan-and-Execute是为了「把事做完」，Reflection是为了「把事做好」，优势在于输出质量明显提高，幻觉、逻辑错误、细节遗漏都会减少，对严谨性要求高的场景效果尤其明显，代价是每添加一次Reflection就多一次甚至多次LLM调用，成本和延迟都会增加。如果没有轮次限制会陷入」为了改而改」的死循环。

### 动态Replan和Reflexion
- 动态Replan：解决Plan-and-Execute的核心痛点，即计划定死在中途遇到意外怎么办。动态Replan的做法是在每个步骤执行完后，把当前结果和剩余计划一起交给规划模块，让它判断「原计划是否合理，是否需要调整」，如果需要就生辰新的计划进行替换。这样既保留了Plan-and-Execute先规划再执行的结构优势，又不会因为计划太僵硬而因意外情况翻车。代价是每一步都多一次「重新评估计划」的LLM调用，增加token消耗。
- Reflexion：把Reflection的自我反思推到更深的层次，它不仅检查输出对不对，还会把每次错误的原因总结存入记忆中，下次遇到类似任务时会把总结拼入上下文传入LLM，避免重复犯错。

### 选型指南
工程最佳实践是：先用 ReAct 快速验证效果，确认任务能跑通之后，再根据 token 消耗和延迟的实际数据，决定要不要切换到 Plan-and-Execute 或者叠加 Reflection。不要一上来就选最复杂的方案，先跑起来再优化。这种三层嵌套的架构听起来复杂，但其实在 LangGraph 这类框架里实现起来很自然，很多生产级的 Agent 系统都是这么搭的。

- 任务不复杂、流程不固定、需要实时调整的，直接用 ReAct，够用就好，别搞复杂的。
- 任务很长、容易跑偏、需要整体结构清晰的，上 Plan-and-Execute，先把计划定清楚再执行。
- 如果执行过程中经常遇到意外需要调整计划，就加上动态 Replan。
- 输出要求高、不能出错的，在前两者基础上叠加 Reflection 做自我检查。
- 如果还需要跨任务积累经验、避免重复犯错，就用 Reflexion 把失败教训沉淀下来。

## 复杂任务怎么做任务拆分
### 简要回答
需要任务拆分的原因是LLM一次性处理太复杂的任务容易出错，把大任务拆成小步骤，每步聚焦一件事，准确率会明显提升。拆分的方式有两种：
- 静态拆分：提前把步骤写死
- 动态拆分：让LLM自己根据目标规划步骤，更灵活但也难以控制

拆分完后步骤间可能还会有依赖关系，我的经验是把能并行的步骤并发跑，端到端延迟可以降低很多。

### 为什么要拆分任务
LLM的工作台是context window，是有大小限制的，能同时处理的信息量是有上限的。任务越大、中间状态越多、桌面就约混乱，任务拆分要解决的就是「桌面」太乱这个问题。把一个大目标切成多个小步骤，每个步骤只做一件事，LLM 的全部注意力都集中在这一件事上，桌面保持干净，质量自然高。

还有一个好处：每一个步骤都是独立的输出，可以被单独检查和验证，某个环节出错不需要从头跑整个任务。

### 任务拆分思路
任务拆分有两种思路：自己来拆，或让LLM来拆。注意将「任务拆分」与CoT和ToT的概念做区分，后者是推理范式，前者是任务规划，二者的粒度和目标不同。

#### 静态拆分
开发者提前把任务流程设计好，固定成一个确定的Workflow，优点是行为完全可预测，出了问题知道是哪一步的问题，好排查；缺点是灵活性差，遇到设计流程外的情况就容易卡住。

#### 动态拆分
把任务拆解交给LLM来做，给LLM制定一个目标，由LLM先输出执行计划，再按计划一步步执行，这是Plan-and-Execute模式的核心思想。整个 Plan-and-Execute 流程分三个阶段，每个阶段的角色和职责都非常清晰。
- 规划：这一步只做规划，不做任何实际执行，LLM全部精力在规划上。
- 执行：根据计划表逐步执行每个步骤，每一步都把前面所有步骤的结果作为context传入LLM，保证每一步都能看到完整历史。
- 汇总：所有步骤执行结束后，将各步骤产出汇总，生成最终输出。这一步不仅是拼接，还要解决各步骤的衔接问题，确保最终输出是一个连贯的整体。

动态拆分的优势是灵活性强，LLM可以根据具体任务的特点制定最合适的计划；缺点是规划质量不稳定，规划一旦出问题后续执行步骤都建立在错误的基础上。

步骤拆分好之后还有一件重要的事：分析步骤之间的依赖关系。有些步骤有前置步骤依赖，有些步骤独立可以并行执行，识别出可以并行的步骤是降低总耗时的关键。要让并行真正落地，前提是把依赖关系画成一张有向无环图（DAG），每个节点是一个步骤，边表示依赖，没有依赖的节点就能同时执行，依赖的节点就必须等前置节点完成，这一步直接决定了并行优化的天花板。

任务拆分不是越细越好，粒度把握很重要，拆分太细有两个代价：
- 步骤过多：LLM调用次数多，总token消耗增加
- 步骤太碎：每步只做极小的事，LLM无法关注到全局，各部分容易衔接生硬。

任务拆分太粗则又回到原来的问题：每步负责的事太多，与其他步骤不互相依赖。出错概率上升，无法定位问题。

实践中通常把「原子操作」作为划分单步的标准：这个步骤只做一件独立的事，边界清晰，做完有明确的输出，和其他步骤不互相依赖。

### 自适应拆分：做不好就继续拆
静态拆分与动态拆分都基于一个隐含的假设：拆分在任务开始的时候就一次性完成了，执行过程中不会再调整拆分粒度，但实际情况并没有这么理想。

最佳工程实践是：不在一开始就把所有步骤的粒度定死，而是在执行过程中根据每一步的实际难度动态调整。

核心逻辑很简单：先让执行器尝试完成当前任务，执行结果好就继续下一步，不做多余拆分；如果执行的不好，就把执行的不好的步骤交给规划器，让规划器进一步拆分成更小的子任务，再对每个子任务重复同样的流程。整个过程像一棵递归展开的任务树，
