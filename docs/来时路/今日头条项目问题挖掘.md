# 今日头条项目问题挖掘
## 响应式布局怎么实现的，如何适配不同端的现实效果
项目采用的是TailwindCSS，默认先写移动端的响应式方案，基础类默认服务小屏，再通过`sm:、md:、lg:、xl: `表示屏幕达到对应最小宽度后生效。
- 采用flex弹性布局、grid网格布局、`max-w-*`等构建流式布局，避免固定宽高导致溢出。`max-w-*`就是CSS中的`max-width`。
- 创作页在大屏显示完整双栏，小屏降级为只显示ai创作单栏，这也是响应式布局的一个缺陷，不同设备可能造成功能缺失，无法完整显示。
- 对于长内容采用overflow-y-auto，也就是CSS中的overflow-y: auto;，当内容超出容器高度时，出现滚动条，保证内容不被遮挡。
- 图片使用max-w-full和object-contain，避免横向溢出，object-contain就是CSS中的object-fit: contain;，保证图片在容器内完整显示。

## TailwindCSS是什么
Tailwind CSS 是一个原子化、工具类优先的 CSS 框架。它不需要写业务CSS，而是提供大量预定义的工具类，通过组合来快速搭建响应式、可定制的用户界面。实际原理是TailwindCSS在构建阶段扫描源码中实际使用的类名，生成对应CSS，因此打出的包不会包含整套工具类。代价是编写的JSX的className会非常长，代码可读性差。通常可以通过组件拆分、cn()方法条件类合并，以及将重复组合抽成公共组件或 @apply，来维持可读性。

## shadcn/ui与antd或者elementUI的区别在哪里，为什么选择了使用shadcn/ui
antD和elementUI都是完整的组件库，而shadcn/ui是一个基于Radix UI和TailwindCSS封装的，可按需复制到项目的组件源码集合，这就为开发者提供了直接对组件进行修改的可能性，保留 UI 底层控制权，组件行为和DOM完全可控，而不是像antD和elementUI那样受组件库API和内部实现约束。按需安装的特性也减少了打包体积。

选型上如果是后台管理系统，且重度依赖复杂表格、动态表单、日期组件，我会更倾向 Ant Design；如果是 Vue 技术栈，则通常选择 Element Plus。

## 为什么使用Next.js
传统 CSR 中，服务端通常只返回较少内容的 HTML，浏览器还要下载、执行 JS，再请求数据并完成渲染，因此首屏容易出现加载态或空壳，弱网体验较差。

项目选择 Next.js
- 主要利用 SSR / RSC 在服务端完成首屏数据获取和渲染：浏览器首次拿到的 HTML 已经包含主要内容，能更快看到页面，也有利于 SEO。
- 其次，Next.js 适合承担 BFF 层。比如首页所需的文章、作者、榜单等数据，可以在服务端并行请求、聚合并裁剪为页面需要的数据结构；浏览器只需要请求页面或一个聚合接口，不需要自己协调多个后端服务。这样减少客户端的请求编排，也能避免依赖链导致的请求瀑布。
- 另外，第三方服务的 API Key 放在服务端环境变量中，由 Route Handler 或 Server Component 调用。浏览器只拿到渲染所需的结果，避免密钥暴露。

当然，不能把所有组件都 SSR。静态展示、首屏内容优先放服务端；搜索输入、弹窗、点赞、编辑器这类强交互功能放 Client Component。核心是控制 SSR、RSC 和 CSR 的边界，避免不必要的客户端 JS 和服务端重复请求。

## 什么是BFF
BFF即Backend For Frontend，是一种后端架构模式，Nextjs的服务端能力就可以充当“专门服务前端的中间层”。

它位于前端与多个后端服务之间，按页面或终端的实际需要做：
- 接口聚合：合并多个服务的数据；
- 数据裁剪和格式转换：返回前端真正需要的结构；
- 鉴权、权限校验与密钥隔离；
- 屏蔽后端服务拆分和接口变更的复杂度。

在 Next.js 中，Route Handler 很适合实现显式的 BFF API；Server Component 则可以直接在服务端获取并聚合首屏数据。前者返回通常是 JSON，后者的渲染结果会通过 HTML 和 RSC Payload 传递给浏览器。

## 双token无感刷新
这个项目使用 Access Token 和 Refresh Token 实现登录认证及无感刷新。用户登录成功后，服务端会生成两枚 JWT：Access Token 默认有效期是 15 分钟，Refresh Token 默认有效期是 7 天。

Access Token 通过响应体返回，前端保存在 Zustand 内存中；Refresh Token 通过 Set-Cookie 写入浏览器。Refresh Cookie 设置了 HttpOnly，降低 Token 被前端恶意脚本直接读取的风险；生产环境启用 Secure，只允许通过 HTTPS 发送；同时设置 SameSite=Lax，降低部分 CSRF 风险。

Refresh Token 中包含唯一的 jti。服务端不会保存 Refresh Token 明文，而是把 jti、Token 哈希、用户 ID、过期时间和撤销时间保存到数据库。需要注意，jti 标识的是一枚 Refresh Token，不是设备 ID。这样既能校验刷新会话，也能主动撤销 Refresh Token。
前端调用普通业务接口时，会在 Authorization: Bearer `<access-token>` 请求头中携带 Access Token。服务端验证它的签名、有效期以及 Token 类型，验证成功后从 Payload 中获得用户身份。

对普通请求，如果 Access Token 过期导致服务端返回 401，统一 API 封装会调用 Refresh 接口。刷新成功后，服务端返回新的 Access Token，同时采用 Refresh Token Rotation 签发新的 Refresh Token，并撤销旧 Refresh Token；前端随后使用新的 Access Token，把原业务请求重试一次。

如果多个请求同时收到 401，前端通过模块级的 refreshPromise 实现 SingleFlight。第一个请求真正发起刷新，其他请求等待同一个 Promise，而不是分别调用 Refresh 接口。刷新成功后，它们共享新的 Access Token，并分别重试各自的原请求。

这么做很重要，因为 Refresh Token 采用一次性轮换。如果多个请求同时使用旧 Refresh Token，第一个请求成功后就会撤销旧 Token，后续刷新可能失败并清除登录状态。共享 Promise 可以避免单个标签页内的这种并发轮换冲突。

对 SSE 请求，因为长连接建立后不方便再走普通的 401 重试流程，所以前端会在建立连接前解析 Access Token 的过期时间。如果 Token 已经过期，或者距离过期不足 30 秒，就先刷新 Token，再发起 SSE 请求。

如果 Refresh Token 本身已经过期、被撤销或者不合法，那么无感刷新就无法继续。所有等待同一个刷新 Promise 的请求都会收到刷新失败结果，前端统一清除认证状态，要求用户重新登录。
