# 今日头条项目问题挖掘
## CSS相关
### 响应式布局怎么实现的，如何适配不同端的现实效果
项目采用的是TailwindCSS，默认先写移动端的响应式方案，基础类默认服务小屏，再通过`sm:、md:、lg:、xl: `表示屏幕达到对应最小宽度后生效。
- 采用flex弹性布局、grid网格布局、`max-w-*`等构建流式布局，避免固定宽高导致溢出。`max-w-*`就是CSS中的`max-width`。
- 创作页在大屏显示完整双栏，小屏降级为只显示ai创作单栏，这也是响应式布局的一个缺陷，不同设备可能造成功能缺失，无法完整显示。
- 对于长内容采用overflow-y-auto，也就是CSS中的overflow-y: auto;，当内容超出容器高度时，出现滚动条，保证内容不被遮挡。
- 图片使用max-w-full和object-contain，避免横向溢出，object-contain就是CSS中的object-fit: contain;，保证图片在容器内完整显示。

### TailwindCSS是什么
Tailwind CSS 是一个原子化、工具类优先的 CSS 框架。它不需要写业务CSS，而是提供大量预定义的工具类，通过组合来快速搭建响应式、可定制的用户界面。实际原理是TailwindCSS在构建阶段扫描源码中实际使用的类名，生成对应CSS，因此打出的包不会包含整套工具类。代价是编写的JSX的className会非常长，代码可读性差。通常可以通过组件拆分、cn()方法条件类合并，以及将重复组合抽成公共组件或 @apply，来维持可读性。

### Styled Components、TailwindCSS选型你怎么考虑
#### Styled Components
CSS-in-JS（把 CSS 写在 JS 中）。

- **特点**：
  - 样式与组件绑定，局部作用域，不会污染全局。
  - 支持动态样式（根据 props 改变样式）。
  - 支持主题（ThemeProvider）和复用组件样式。
- **优点**：组件化、动态样式强、便于主题管理。
- **缺点**：运行时生成 className，有性能开销；调试类名不直观。
- **适用场景**：交互复杂、动态样式多、需要多套主题的中大型应用。

#### TailwindCSS
原子化 CSS 工具类。

- **特点**：
    - 使用一组小类名组合实现样式（如 `text-center`, `bg-red-500`）。
    - 静态 class，无运行时开销，JIT 模式只打包使用到的类。
    - 高度一致、易维护，适合快速开发。
- **优点**：快速布局、高性能、避免全局样式冲突
- **缺点**：HTML 类名较长，动态样式需额外处理。
- **适用场景**：后台管理系统、大量列表/表格、高性能 UI，追求开发效率的项目。

### shadcn/ui与antd或者elementUI的区别在哪里，为什么选择了使用shadcn/ui
antD和elementUI都是完整的组件库，而shadcn/ui是一个基于Radix UI和TailwindCSS封装的，可按需复制到项目的组件源码集合，这就为开发者提供了直接对组件进行修改的可能性，保留 UI 底层控制权，组件行为和DOM完全可控，而不是像antD和elementUI那样受组件库API和内部实现约束。按需安装的特性也减少了打包体积。

选型上如果是后台管理系统，且重度依赖复杂表格、动态表单、日期组件，我会更倾向 Ant Design；如果是 Vue 技术栈，则通常选择 Element Plus。

### 深浅主题模式切换怎么实现
在global.css全局css文件中通过:root伪类定义浅色主题的CSS变量，通过.dark类来覆盖同一组变量，这些变量实际是TailwindCSS可使用的词义化token，比如--background，使用时就是bg-background。切换主题只需要查看根节点是否有.dark类即可，当切换时引用这些样式变量的组件会由浏览器自动重新计算样式。

用户的主题偏好存储在localStorage中，在next.js最顶层的layout.tsx即RootLayout的header中，通过script标签首先在页面加载时读取localStorage的值，决定是否给根节点添加.dark类，而不是放在useEffect中，不然可能会出现先白再黑的闪烁。用户切换主题时，更新localStorage并切换根节点的.dark类。

由于服务端生成的 `<html>` 没有 dark，但客户端脚本可能在 Hydration 前添加它，所以使用`<html suppressHydrationWarning>`来避免 React 对根节点这处预期内的属性差异发出水合警告。

## Next.js相关
### 为什么使用Next.js
传统 CSR 中，服务端通常只返回较少内容的 HTML，浏览器还要下载、执行 JS，再请求数据并完成渲染，因此首屏容易出现加载态或空壳，弱网体验较差。

项目选择 Next.js的原因是：
- 主要利用 SSR / RSC 在服务端完成首屏数据获取和渲染：浏览器首次拿到的 HTML 已经包含主要内容，能更快看到页面，也有利于 SEO。
- 其次，Next.js 适合承担 BFF 层。比如首页所需的文章、作者、榜单等数据，可以在服务端并行请求、聚合并裁剪为页面需要的数据结构；浏览器只需要请求页面或一个聚合接口，不需要自己协调多个后端服务。这样减少客户端的请求编排，也能避免依赖链导致的请求瀑布。
- 另外，第三方服务的 API Key 放在服务端环境变量中，由 Route Handler 或 Server Component 调用。浏览器只拿到渲染所需的结果，避免密钥暴露。

当然，不能把所有组件都 SSR。静态展示、首屏内容优先放服务端；搜索输入、弹窗、点赞、编辑器这类强交互功能放 Client Component。核心是控制 SSR、RSC 和 CSR 的边界，避免不必要的客户端 JS 和服务端重复请求。

### 什么是BFF
BFF即Backend For Frontend，是一种后端架构模式，Nextjs的服务端能力就可以充当“专门服务前端的中间层”。

它位于前端与多个后端服务之间，按页面或终端的实际需要做：
- 接口聚合：合并多个服务的数据；
- 数据裁剪和格式转换：返回前端真正需要的结构；
- 鉴权、权限校验与密钥隔离；
- 屏蔽后端服务拆分和接口变更的复杂度。

在 Next.js 中，Route Handler 很适合实现显式的 BFF API；Server Component 则可以直接在服务端获取并聚合首屏数据。前者返回通常是 JSON，后者的渲染结果会通过 HTML 和 RSC Payload 传递给浏览器。

### CSR和SSR的HTML解析区别在哪里
#### CSR客户端渲染
服务端只返回一个HTML空壳，浏览器下载JS并执行后，JS会去请求数据接口，拿到数据后再生成DOM并渲染到页面上。浏览器解析HTML时，看到的内容是空白的，直到JS执行完才会显示内容。
```txt
下载 HTML
→ HTML Parser 生成空壳 DOM
→ 下载、解析、执行 JavaScript
→ React 创建 Fiber 树
→ 请求业务数据
→ React 创建文章列表 DOM
→ 页面显示完整内容
```

#### SSR服务端渲染
服务端在渲染时就已经执行了React和数据请求，并生成了完整的HTML，浏览器解析HTML时就能看到完整内容，JS下载后再绑定事件和恢复状态
```txt
下载 HTML
→ HTML Parser 直接生成包含文章内容的 DOM
→ 浏览器可以提前绘制页面
→ 下载、执行客户端 JavaScript
→ React 创建 Fiber 树
→ Hydration 关联已有 DOM
→ 页面恢复交互
```

#### 总结
CSR 和 SSR 使用的是同一个浏览器 HTML Parser，差别不在解析规则，而在输入内容。CSR 返回空壳，业务 DOM 由客户端 JavaScript 创建；SSR 返回完整首屏 HTML，浏览器解析后即可绘制，客户端 React 再通过 Hydration 复用并接管已有 DOM。因此 SSR主要缩短内容可见路径，但交互仍要等待客户端代码和水合完成。


### 什么是Hydration水合
Hydration（水合）是指：React 在浏览器端接管服务端已经生成的 HTML，并为它绑定事件和恢复组件状态，使静态页面变成可交互应用。

水合过程中React不会重新创建整棵DOM，而是：
1. 根据客户端组件树遍历现有服务端 HTML。
2. 将 React Fiber 与已有 DOM 节点建立关联。
3. 恢复 state、context 等运行时能力。
4. 绑定事件系统，使页面可交互。

水合的价值是：
- SSR/RSC 的快速内容展示；
- React 客户端组件的交互能力；
- 尽量复用已有 DOM，减少重复创建。

SSR改善的是“什么时候能看见”，而水合则决定了“什么时候能交互”。

### app router和react router的区别
app router做的不仅仅是客户端路由，还包括渲染、数据请求和服务端边界的应用框架能力。app router按照文件目录直接进行路由生成和代码分割，而react router是通过代码进行配置式路由，以及通过lazy()和Suspense实现代码分割。

app router在对应路由文件夹下提供预声明的page.tsx、layout.tsx、loading.tsx、error.tsx等文件，分别对应路由的页面、布局、加载态和错误态。react router则是通过JSX配置路由，路由组件和布局组件没有明确的约束，需要通过loader状态和errorElement来处理加载态和错误态。

最关键的区别是服务端边界，在app router中，路由层级下的page.tsx默认是RSC，这样就可以在服务端就完成组件的数据请求和渲染；而在react router的传统SPA模式下，需要通过useEffect在客户端发起数据请求，服务端只返回一个空壳HTML。

### 为什么SSR有利于SEO
搜索引擎爬虫在抓取网页时，通常只会解析 HTML 内容，而不会执行 JavaScript。CSR（客户端渲染）模式下，服务端返回的 HTML 只是一个空壳，主要内容需要通过 JavaScript 执行后才能生成，这会导致爬虫无法获取到页面的实际内容，从而影响搜索引擎的索引和排名。但是SSR不一样，它在服务端就完成了数据请求生成了完整的HTML，爬虫可以直接抓取到页面的主要内容，从而有利于SEO。

CSR的抓取链路是：
```txt
获取 HTML 空壳
→ 下载并执行 JavaScript
→ 请求业务数据
→ React 渲染内容
→ 爬虫建立索引
```

SSR的抓取链路是：
```txt
服务端获取数据并生成 HTML
→ 爬虫解析 HTML
→ 读取正文、链接和元信息
→ 建立索引
```

### Next.js的打包器是什么
Next.js现在使用的打包器是turbopack，它是用Rust编写的现代打包器，它不会在开发服务器启动时将所有模块打包成一个大包，而是根据访问路由按需打包，采用增量计算和懒编译的策略。

当修改文件时，turbopack根据细粒度缓存只重新计算受影响的依赖，而不是重新构建完整bundle，并使用统一依赖图处理Next.js的多种目标：
- RSC
- 客户端组件
- Node Server
- 浏览器Chunk

在Webpack中每个环境都是一次独立的编译、一张独立模块依赖图、一套独立的chunk和缓存。从一个源文件中可能会分裂出以上四种环境并行的图，这意味着如果对其中一个文件做了修改，可能造成多张依赖图都需要重新计算，导致编译时间增加。更麻烦的是这些图需要手工对齐，需要在图之间对引用的模块进行映射匹配。

而Turbopack只维护一张依赖图，所有环境都从这一张依赖图中取自己需要的部分，在这张依赖图中，节点不只是文件，而是文件+环境组成的一个计算任务。不同环境之间的关联天然内建在图的边里，不需要手工拼接。计算是函数式的，如果输入确定那么输出确定，这就是细粒度缓存的来源。chunk规划在这张图上进行。



## 性能优化
### 采用服务端预取与接口并行
首页组件是异步 Server Component即RSC。在服务端渲染页面前，利用promise.all直接并发请求后端接口，两个接口的等待时间也由耗时之和降低为最慢接口耗时。服务端会把首页渲染需要的文章流数据和热门榜单数据的请求结果封装为initialData，传给客户端组件CSC，在客户端首次渲染时直接使用initialData，避免了客户端发起额外请求，减少了首屏加载时间。所以我的首屏加载流程不是：
```txt
浏览器加载JS -> Hydration水合 -> useEffect请求文章流数据 -> 再渲染文章流组件
```
而是服务端取得数据后直接返回带有文章流数据的HTML，减少客户端请求瀑布和首屏空白时间。流程为：
```txt
服务端执行 RSC
→ 并行获取文章流和热门榜单
→ 返回包含首屏内容的 HTML
→ 浏览器先展示 HTML
→ 下载客户端组件 JS
→ React Hydration
→ 绑定点击、点赞、切换排序等交互
```

事实上首页组件主要需要与三个数据接口进行交互获取数据，其中新闻热点接入的是GNEWs第三方接口，之前将这个接口也放入了promise.all发现首屏会长时间处于fallback组件状态，很久才渲染真正的首页组件出来，后来通过devTools的performance录制和network分析画面帧和接口耗时发现GNEWs接口耗时过长导致promise.all迟迟无法完成状态变化，且这个接口的稳定性不可控，于是把这个接口独立移入了客户端组件异步加载，且额外用promise.race做了超时竞争、重试、AbortController取消，并用骨架组件撑起其内容空间。

### Next/Image是怎么优化图片加载的。
Next/Image 的优化核心是：让图片按正确时机、正确尺寸、正确格式加载，同时提前预留布局空间。

1. 非首屏图片懒加载：Image组件主要使用在了首页文章卡片的封面配图，没有设置priority/preload 的 Image 默认懒加载，浏览器只在图片接近视口时才发起请求，避免文章列表下方的图片与首屏 CSS、JS、字体等关键资源竞争带宽。
2. 响应式图片选择：通过为Image设置sizes属性，让Next.js根据配置生成不同尺寸的候选图片及srcset，浏览器结合`视口宽度 + sizes + 设备像素比 DPR`选择合适的资源
3. 服务端图片转换：在next.config.ts中配置了images.formats为['image/avif', 'image/webp']，Next.js会根据浏览器的Accept 请求头选择支持的现代格式，减少图片体积。
```txt
浏览器 → /_next/image?url=...&w=...&q=...
        → 获取原图
        → 缩放、压缩、格式转换
        → 返回优化后的图片
```
4. 减少CLS（布局偏移）：为Image设置width和height使其在图片下载前预留空间，避免图片加载完成后把正文向下推。减少图片加载完后的回流重绘。
5. 缓存优化结果：优化后的不同尺寸和格式可以被 Next.js 图片优化层缓存。后续请求相同图片、宽度和质量时，不需要重复转换，还可结合响应头和 CDN 缓存降低回源成本。

### 路由级代码分割按需加载非首屏模块的原理
主要用了两种按需加载方式：
- Next.js本身的文件即路由的自动路由级代码分割
- next/dynamic的组件级懒加载

#### 路由级代码分割
根据左侧菜单栏的各个菜单项进行了路由配置，每个 page.tsx 都是独立路由入口，Next.js 分别分析其依赖图。只有被首页及其共享布局静态依赖的模块，才会进入首页初始依赖范围。首页不会因为存在对创作页、用户页等组件的import就将对应代码也放入首页首屏包。因为这些组件属于自己各自的路由段，用户访问首页时，主要加载首页对应的客户端代码；只有执行了对应组件的路由跳转即：
```js
// 点击创作页跳转
router.push('/create')
// 点击用户页跳转
router.push('/materials')
// 点击作品管理页跳转
router.push('/work')
...
```
才会获取对应路由的RSC Payload和对应客户端的JS Chunk。确保其他功能页的数据与交互逻辑不会进入首页首屏JS。

因为顶栏Header和左侧栏Sidebar是每个路由页面共享的公共布局layout，所以将他们提升为Shell Component，切换的主界面内容组件main作为children传入。传入方式是根据Next.js的app router通过文件目录层级生成路由树，作为公共组件的layout是各界面路由的前一步公共路由，当切换功能页时，App Router会比较新旧路由树的segment，会对相同的部分复用，而不同的segment会触发对应的RSC Payload请求和客户端JS Chunk加载。这样就实现了路由级代码分割按需加载非首屏模块。
```txt
旧：Root → workspace → home
新：Root → workspace → inspiration
```

#### next/dynamic的组件级懒加载
由于登录弹窗是个额外的在所有界面组件上方的窗口组件，它不是独立的路由，所以我使用了next/dynamic的组件级懒加载，登录弹窗组件的import会单独形成一个chunk，只有在用户点击登录按钮时才会加载这个chunk，避免登录弹窗的JS和CSS进入首页首屏包。

dynamic本质是对React.lazy、Suspense、import()的封装，提供了更多配置选项，比如SSR开关、加载态组件等。它的原理是：当组件被渲染时，动态import会返回一个Promise，React Suspense会等待这个Promise resolve后再渲染组件，同时可以显示一个fallback组件作为加载态。这一点有点像React.lazy。

next/dynamic 在构建阶段通过静态分析 import() 建立模块与 Chunk 的映射，将目标 Client Component 拆出首屏 Bundle；运行时组件首次渲染会触发 Chunk 请求，未完成的 Promise 通过 React.lazy/Suspense 机制挂起，加载完成后重新调度对应 Fiber。Next.js 在此基础上增加了预加载、loading UI 和 ssr:false 等能力。动态导入优化的是 JS 的加载时机，ssr:false 才表示跳过服务端预渲染。

## 文件上传
### 项目里的素材文件上传是怎么做的
封装一个fileAsDataUrl函数实现利用Promisify异步读取文件成base64格式的Data URL，将Data URL连同文件名传给后端POST接口，后端先通过正则获取matches信息，matches[1]是文件类型，matches[2]是base64编码的文件内容。后端将base64的文件内容解码成二进制流，将二进制流通过saveUpload方法存入RustFS对象存储，返回一个URL；如果没有配置RustFS则返回本地uploads文件夹路径。前者成功配置RustFS对象存储产生的URL是一个资源代理地址，并没有真的指向RustFS中的二进制文件，当要获取图片时，真正的流程是通过GET接口获取数据库中图片的元信息包括URL，URL的/api/被Next.js或Nginx的代理将接口拦截转发给Express的/assets/:scope/:filename接口，通过解析URL中的scope和filename拼接后作为key，去RustFS中利用AWS S3 SDK的GetObjectCommand获取asset，其中包括文件二进制流body和content-type以及缓存标识etag，最后设置好相应头部的content-type和cache-control，把body返回给浏览器。浏览器读到响应头部的content-type后就能正确加载图片了。

### 为什么要用到RustFS
因为我选择RustFS对象存储来负责大文件与高吞吐 I/O，而数据库PG只负责存结构化的元数据和事务
1. 避免数据库膨胀：如果把图片存成 PostgreSQL bytea 或 MongoDB Binary/GridFS，文件会进入数据库数据文件、WAL/复制链路和备份体系。素材量增长后，会导致备份、恢复、主从复制和查询维护成本明显上升。
2. 对象存储更适合文件 I/O：素材访问主要是“根据 key 读取完整文件”，不需要关系查询。RustFS 基于对象 key 存取，适合大对象和流式传输；数据库更擅长索引查询、关联和事务。
3. 扩展方式不同：业务数据增长通常需要优化索引、分库分表；素材文件主要消耗容量和带宽。分开后可以独立扩容 RustFS，而不会因为图片增加去扩容数据库计算节点。
4. 便于缓存与资源分发：项目代理接口会返回 Content-Type、Cache-Control 和 ETag，浏览器可以正确渲染并进行协商缓存。后续还可以把资源代理接入 CDN，数据库中的素材记录无需改变。
5. S3 兼容降低迁移成本：RustFS 提供 S3 兼容接口，项目通过 AWS S3 SDK 的 PutObject/GetObjectCommand 操作。以后迁移到 AWS S3、MinIO 或其他兼容存储，业务层改动较小，同时 RustFS 可以私有化部署，适合控制成本和数据归属。

### 为什么没用MinIO
其实MinIO和RustFS都是S3兼容的对象存储，MinIO是Go语言实现的，RustFS是Rust语言实现的。二者都可以使用，且我的项目只是简单使用了对象存储的上传、下载和删除操作，单纯是因为MinIO从 Apache 2.0 统一切换到了 GNU AGPLv3，而RustFS是Apache 2.0协议，意味着我可以把RustFS嵌进闭源产品、二次开发、闭源部署，没有协议层面的商业风险，对商业用法更友好，尽管我这个是一个挂在github的开源项目。

### 可不可以用数据库存本地url的方式
数据库存本地文件 URL 在单机环境可行，因此项目把它作为 RustFS 未配置时的 fallback；但生产环境存在多实例文件不共享、容器重建丢失、扩容备份困难等问题，所以正式方案使用对象存储，数据库只保存稳定的逻辑地址和元信息。




## 用户登录
### 密码是怎么存的
用户注册后，并不是在数据库中明文存储密码，而是用Node.js的crypto模块的scrypt进行加盐哈希。流程如下：
```txt
用户输入密码
→ 生成随机 Salt
→ scrypt(密码, Salt) 派生哈希
→ 数据库存储 Salt:Hash
```
当后端取得用户密码原文时，先生成16字节的随机salt并转为32位的16进制字符串，然后用scrypt结合salt和密码原文派生出64字节的哈希值，再转为128位的16进制字符串。最后把salt和hash拼接成salt:hash的形式存入数据库。salt并不需要保密，它是为了让相同密码产生不同的哈希，防止彩虹表攻击，避免两个用户使用相同密码时数据库存储相同哈希的情况。

#### 用户登录的流程是怎样的
当用户登录时，项目从数据库取出对应userId的password_hash，拆出salt和hash，用用户输入的密码原文与拆出的salt再次进行scrypt派生哈希，然后与数据库存储的hash进行比较，如果一致则登录成功，否则登录失败。

#### 为什么用scrypt而不是bcrypt或SHA256或MD5
SHA256和MD5是快速哈希，如果攻击者用GPU进行暴力破解，能在短时间内尝试大量密码。bcrypt 和 scrypt 是专门的密码派生函数，通过可调计算成本抵抗暴力破解，其中 scrypt 还具有内存困难特性。项目因此用 scrypt 存密码，用 SHA-256 保存 Refresh Token 的不可逆摘要。

## 双token无感刷新
这个项目使用 Access Token 和 Refresh Token 实现登录认证及无感刷新。用户登录成功后，服务端会签发两枚 JWT：Access Token 默认有效期是 15 分钟，Refresh Token 默认有效期是 7 天。他们使用不同的secret签名，且在Payload中设置不同的Token类型标识。防止错用Refresh Token去访问普通业务接口，或者错用Access Token去刷新会话。

Access Token 通过响应体返回，前端保存在 Zustand 内存中；Refresh Token 通过 Set-Cookie 写入浏览器缓存。Refresh Cookie 设置了 HttpOnly，阻止JavaScript通过document.cookie接触Cookie，降低 Token 被前端恶意脚本直接读取的风险即XSS攻击风险；生产环境启用 Secure，只允许通过 HTTPS 发送；设置path到指定鉴权路径使其不会跟随所有业务请求；同时设置 SameSite=Lax，降低跨站请求伪造 CSRF 风险。

Refresh Token 的payload中包含唯一的 jti。jti是一个uuid，服务端不会保存 Refresh Token 明文，而是把 jti、Token SHA256哈希、用户 ID、过期时间和撤销时间保存到数据库。这样既能校验刷新会话，也能主动撤销 Refresh Token。 Refresh Token便不是一个完全无状态的JWT了，而是一个半状态的JWT。服务端在刷新时会验证 jti 是否存在、是否过期、是否被撤销。前端调用普通业务接口时，会在 Authorization: Bearer `<access-token>` 请求头中携带 Access Token。服务端验证它的签名、有效期以及 Token 类型，验证成功后从 Payload 中获得用户身份。

封装一个apiResponse请求，普通请求request会携带Cookie（Refresh Token）和Authorization头（Access Token），如果 Access Token 过期导致服务端返回 401，统一 apiResponse封装会调用 Refresh 接口。浏览器通过 credentials: 'include' 自动携带 HttpOnly Cookie。前端代码不需要、也无法读取 Refresh Token。刷新成功后，服务端返回新的 Access Token，同时采用 Refresh Token Rotation 签发新的 Refresh Token，并撤销旧 Refresh Token；前端随后使用新的 Access Token，把原业务请求重试进行一次request。

如果多个请求同时收到 401或者主动预刷新Access Token时，前端通过模块级的单例变量refreshPromise 实现共享Promise的 SingleFlight单飞。而根据JS单线程的特性，第一个请求真正发起刷新，其他请求等待同一个 Promise，而不是分别调用 Refresh 接口，防止发生竞态。刷新成功后，它们共享新的 Access Token，并分别重试各自的原请求。

这么做很重要，因为 Refresh Token 采用一次性轮换。如果多个请求同时使用旧 Refresh Token，第一个请求成功后就会撤销旧 Token，后续刷新可能失败并清除登录状态。共享 Promise 可以避免单个标签页内的这种并发轮换冲突。后端对Refresh Token的撤销与更新放入了事务中，保证了原子性。从BEGIN开始首先用FOR UPDATE锁定旧Refresh Token，同样是防止并发更新Refresh Token导致产生不同的新Token；查询用户在数据库中的登录状态，如果用户status不是active，则ROLLBACK并清理Cookie从而让前端重新登录；如果用户状态正常，则将旧的Refresh Token标记为revoked_at = NOW()，并签发新的Access Token和新的Refresh Token，将新的Refresh Token的jti和hash写入数据库，COMMIT事务。这样就保证了Refresh Token Rotation的原子性。

总体是采用前端单飞 + 后端事务行锁的方式，保证了Refresh Token Rotation的安全性和一致性。

对 SSE 请求，因为长连接建立后不方便再走普通的 401 重试流程，所以前端会在建立连接前解析 Access Token 的过期时间。如果 Token 已经过期，或者距离过期不足 30 秒，就先刷新 Token，再发起 SSE 请求。

### 为什么不采用单token而采用两个token
单token本身无状态的特性，让它无法主动被撤销，如果被截获只能通过黑名单手动添加拦截，或者等过期时间到期才能失效。单token的过期时间如果设置太长，攻击者有更长的攻击窗口；如果设置太短，用户频繁登录体验差。双token方案中，Access Token有效期短，Refresh Token有效期长，且Refresh Token可以被服务端主动撤销。即使Access Token被截获，它的有效期也很短；即使Refresh Token被截获，它在下一次刷新时就会被撤销，无法再使用。

### 为什么把refresh token放在cookie里
因为Refresh Token是一个长期凭证，如果将其存入浏览器内存或localStorage，前端JS就可以直接访问它，这样一旦页面被注入恶意脚本，攻击者就能直接获取Refresh Token，并在其他设备长期刷新 Access Token。将Refresh Token放在HttpOnly Cookie中，前端JS无法访问它，降低了XSS攻击的风险。

### Refresh Token Rotation是什么，作用是什么
这里并没有说在用户登录后一直持有一个refresh token直到过期销毁或者用户主动退出，而是每次用refresh token去刷新access token时，服务端都会签发一个新的refresh token，并撤销旧的refresh token。具体流程是：
1. 验证旧的refresh token的signature，看看是否有效，是否过期，是否被撤销。
2. 根据旧的refresh token的jti和token hash去数据库查找对应的refresh token记录，确认它是有效的、未过期。
3. 将旧Refresh Token的记录标记为撤销，防止它被再次使用。
4. 签发新的Access Token和新的Refresh Token，新的Refresh Token会有新的jti和hash，并保存到数据库。
5. 用新的Refresh Token Cookie覆盖旧的Refresh Token Cookie，确保浏览器只持有最新的Refresh Token。
6. 返回新的Access Token给前端，前端继续使用新的Access Token进行后续请求。

#### 这样做的好处
- 缩短了Refresh Token的有效期，降低被盗用的攻击窗口。
- 因为Refresh Token的状态（jti、hash、revoked_at）被存入了数据库成为半状态的JWT，服务端可以主动撤销Refresh Token，防止被滥用。
- 防止Refresh Token被重放攻击。即使攻击者截获了旧的Refresh Token，它在下一次刷新时就会被撤销，无法再使用。
- 多端会话独立管理。
- 用户登录态无感刷新。

#### 为什么使用事务和For Update锁
因为 Refresh Token 采用一次性轮换。如果多个请求同时使用旧 Refresh Token，第一个请求成功后就会撤销旧 Token，后续刷新可能失败并清除登录状态。共享 Promise 可以避免单个标签页内的这种并发轮换冲突。后端对Refresh Token的撤销与更新放入了事务中，保证了原子性。从BEGIN开始首先用FOR UPDATE锁定旧Refresh Token，同样是防止并发更新Refresh Token导致产生不同的新Token；查询用户在数据库中的登录状态，如果用户status不是active，则ROLLBACK并清理Cookie从而让前端重新登录；如果用户状态正常，则将旧的Refresh Token标记为revoked_at = NOW()，并签发新的Access Token和新的Refresh Token，将新的Refresh Token的jti和hash写入数据库，COMMIT事务。这样就保证了Refresh Token Rotation的原子性。

### 如果Access Token失效了，但这时挂起了一堆请求，怎么处理？
如果 Access Token 失效时同时挂起很多请求，不能让每个请求都各自刷新一次，否则会出现“刷新风暴”，甚至因为 Refresh Token 轮换导致后续刷新全部失败。这个项目使用的是：共享刷新 Promise，也叫 SingleFlight（单飞）机制。

#### 如果Access Token刷新失败怎么办
如果 Refresh Token 本身已经过期、被撤销或者不合法，那么无感刷新就无法继续。所有等待同一个刷新 Promise 的请求都会收到刷新失败结果，前端统一清除认证状态，要求用户重新登录。

## 可追踪Agent Workflow
### 可追踪Agent Workflow是什么
本质上它是一个agentic workflow。让agent来自动完成一串任务。是一个可记录、可回放、可审计、可中断恢复的工作流系统。agent本身并不是一个更聪明的聊天机器人，而是由LLM参与决策、由程序负责执行与约束的任务系统。可跟踪agent workflow就是：让AI在内容生成、审核、改写这条业务链路中工作，但是每一步都不能脱离工程系统的控制。

对于整个内容生产过程来说：`生成文案 → 规则审核 → LLM 改写 → 人工确认 → 发布`。不是让agent一次性调用完模型就结束了，而是把整个过程抽象为：
- Run：一次完整任务实例，例如“为这篇文章生成并审核内容”
- Step：其中一个确定步骤，如“敏感词扫描”“调用 LLM 改写”
- Event：步骤过程事件，如 started、chunk、tool_called、failed、approved

这样做的价值在于：
- 可观测：能知道卡在哪个步骤、模型输入输出是什么、耗时和失败原因。
- 可恢复：某个 Step 失败后可按幂等键重试，不必把整条链路重新执行。
- 可审计：保存 prompt、模型版本、规则版本、工具调用结果和人工操作记录，方便解释“为什么生成了这个结果”。
- 可控：引入状态机和 Human-in-the-loop。例如审核后 Agent 给出改写草稿，但状态停在 waiting_approval，人工确认才会写入新版本并进入发布。
- 可评估：按 Run/Step 聚合成功率、耗时、token、人工介入率、规则命中率，持续优化 workflow。

实现了轻量级持久化状态机：Run、Step、Event 分别记录任务级状态、步骤级输入输出与过程事件，状态支持 queued、running、waiting_user、completed、failed。审核和改写都在服务端异步执行，人工确认前不会写入正式版本。

之所以这是一个agent，是因为从工作流和agent的区别出发，Workflow 解决的是任务编排与可靠执行；Agent 解决的是非确定场景下的决策和工具选择。这个系统以 Workflow 保证可追踪、可恢复和人工兜底，以 Agent 承担生成、审核判断与改写策略。若所有步骤、分支都写死，它只是 LLM 增强的工作流，不能泛化称为 Agent。

它是一个以确定性 Workflow 为骨架、以 LLM 推理和工具结果驱动节点决策的 Agentic Workflow；选择受控编排是为了满足内容审核场景的可审计、可恢复和安全兜底要求。

#### LLM在其中扮演的角色
LLM擅长的是非确定性推断和生成，比如：
- 根据用户主题生成文章
- 判断一段内容可能有什么风险
- 根据审核意见进行改写
- 决定下一步“查资料”还是“产出结果”

但是LLM本身有幻觉风险，输出格式不稳定，可能越权进行工具调用，不能自己记住长期状态。所以在工程上，LLM负责思考和建议，程序负责权限、状态、执行和结果落库。比如哪怕AI说“审核通过”，但不能直接发布内容，还是要通过后端校验规则扫描结果、用户权限和人工审批状态。

### Workflow Runner是做什么
用统一的Workflow Runner来管理三类独立任务Run：
- content_generation：模型路由、生成与轨迹记录；
- content_review：规则扫描、政策检索、LLM 审核与程序决策；
- content_rewrite：生成替换建议、等待用户确认、创建新版本。

### 整个文章从用户输入需求到成功发布是怎样的流程
```txt
AI 生成内容
→ 用户编辑并提交发布
→ 创建待审核版本
→ 规则扫描 + 政策检索 + LLM 审核

```

更细致的审核与改写流程是：
```txt
用户提交作品
  → 创建 Mongo Agent Run
  → PostgreSQL 事务写入内容版本 + review_job
  → 内存队列异步执行审核
  → WorkflowRunner 逐步执行审核
  → 保存审核结论、问题和轨迹
  → 若需修改，生成改写建议
  → 等待用户确认后创建新版本
```

### agent和workflow的区别
workflow决定了按什么流程执行，agent决定了为了完成目标下一步做什么。
| 维度 | Workflow | Agent |
|---|---|---|
| 驱动方式 | 预定义流程驱动 | 目标驱动 |
| 下一步由谁决定 | 代码、规则或状态机 | 通常由模型结合上下文决定 |
| 路径 | 相对固定、可预测 | 可能动态规划、循环和调整 |
| 确定性 | 较高 | 较低 |
| 工具使用 | 在指定步骤调用指定工具 | 模型动态选择工具 |
| 适合场景 | 审核、审批、交易等强约束流程 | 开放检索、复杂任务解决 |
