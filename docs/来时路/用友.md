### 项目
- 数据资源树是什么
```txt
ResourceTree是前端对后端资源目录的内存镜像，ResourceNode 是其中的单个节点。
就目前代码的数据结构而言，资源树真正是一棵有根树，不是图；只是额外维护了一张Map（Scene）作为节点索引。
它是一棵懒加载树，只有在展开节点时才调用后端接口获取直接子节点，不展开的分支不会立即加载完整后代。

ResourceNode同时承载了三类信息：
- 树结构
- 资源身份和类型
- 运行时编辑会话

这么看来ResourceNode不是单纯的树节点，更像是：
资源目录节点 + 资源类型 + 编辑会话容器

ResourceTree管理整棵资源树以及UI状态，树决定了节点间的层级关系，
而scene这个map则实现从O(n)到O(1)查找优化，可以通过节点的key快速找到对应节点。
```
- 节点懒加载是什么？
```txt
节点懒加载是指前端在初始化时，只请求加载根节点及其直接信息，不一次性全量请求整棵树，只有用户展开目录时才请求该节点的子节点。

每个节点有一个aligned属性，初始为false，当请求过一次后会将其设置为true，并将请求的子节点加入到其children属性中，后续再进行折叠展开，不会重复请求后端，而是直接使用内存中该节点的children。scene这个Map索引结构也只存加载出的节点。

为什么采用懒加载：
- 首屏只请求少量节点，让资源树初始化更快
- 避免巨量资源节点渲染
- 减少前端内存占用
- 用户不访问的目录不占用网络请求
- 每个目录可以单独刷新和同步：当在目录下做节点增删改时，只对该路径与后端做数据对齐，而不用对整棵树全量更新。

代价是：每次展开目录需要做短暂等待
```
- 发布订阅设计模式在其中怎么使用的？
    - 发布订阅模式的底层机制
    - 节点如何响应订阅trigger
```txt
本质上ResourceTree和ResourceNode都只是普通可变class对象new出的实例，他们无法驱动React重新渲染。
这里通过发布订阅机制，实现了一个轻量级的“状态变化通知器”。

ResourceTree通过一个Set来订阅更新回调，用Set的好处在于：
- 支持多个组件同时订阅；
- 相同回调不会重复注册；
- 删除订阅的成本较低。

在对应的左侧栏资源树组件中，用useReducer通过结构赋值，定义了一个强制刷新的dispatch reducer即triggerRepaint，用触发便state自增的方式来手动驱动一次React渲染。

发布订阅模式的四个核心能力是：
- 订阅on
- 发布emit
- 取消订阅off
- 只执行一次的订阅once

ResourceNode 本身不直接响应 trigger；ResourceTree 作为可观察状态容器，在节点发生增删、展开、选中或同步后统一发布更新，React 组件通过 useReducer 接收 trigger 并重新读取整棵树的最新节点状态。
```

### AI使用范式
- 目前是怎么使用AI来辅助工作的
- 对于代码标准化如何约束AI
```txt
- 把标准写成可验证的规则，规则越能被 ESLint、TypeScript 或测试验证，约束效果越好。
    - 使用 TypeScript strict 模式
    - 禁止 any 和非空断言
    - 单个函数不超过 40 行
    - 业务逻辑不得写入 React 组件
    - 异步函数必须处理异常
    - 不允许修改公开 API
    - 新增逻辑必须包含单元测试
    - 最终必须通过 npm run lint、npm run typecheck、npm test
- 在仓库中新建AGENT.md建立长期规范
- 针对实现，可以的话给出参考，同时指出反例
- 对于生成新模块，提前约束输出结构，防止AI开始就大面积重构
- 用类型系统比如 TypeScript 来约束数据结构和函数签名，要求AI严格实现接口，不修改类型定义不新增可选字段
- 利用自动化工具形成标准化闭环
    - Prettier格式化
    - ESLint检查代码规范
    - TypeScript strict类型检查
    - Vitest/Jest：行为验证
    - Husky + lint-staged：提交前检查
    - 通过 CI/CD 流程强制执行标准化检查，确保 AI 输出的
- 提示词中严格约束修改范围
```
- 举例说明AI输出的代码有什么缺陷
```txt
常常产出看起来正确、局部能跑，但真实业务约束、生命周期、边界条件和长期维护考虑不足。

- 反复编写相同轮子，没有复用已有工具函数或组件，导致代码冗余。
- 表面优化，为函数和变量都套上useMemo/useCallback，增加复杂度和性能开销。
```

- JavaScript / TypeScript 从源码到执行，大致经历哪些过程？解释器 / 编译器如何工作？
```txt
大致流程上：TypeScritp转JavaScript是编译/转译过程，不是解释器直接执行TypeScript，编译器先把源码解析成AST，再建立符号和作用域关系、执行类型检查，再对AST做“类型擦除”和低版本语法转换，最后遍历AST，打印出JavaScript。

具体来说：
- TypeScript首先通过Scanner将源码字符拆成Token，再由Parser根据语法规则构建AST。然后Binder遍历AST，建立作用域、声明和Symbol之间的关系，TypeChecker基于这些Symbol进行类型推导和类型兼容性检查。
- 检查完成后，Transformer对AST进行转换：删除接口、类型标注等只存在于编译期的节点，并根据target把可选链、异步函数、类等新语法转换成目标JavaScript脚本。最后Emitter或Printer遍历转换后的AST，输出`.js`、`.d.ts`和SourceMap文件。

TypeScript编译器不是逐行替换字符串，而是“源码 → Token → AST → 符号与类型分析 → AST 转换 → JavaScript”，类型信息不会进入运行时。

命令行中使用tsc工具
       ↓
读取 tsconfig.json
       ↓
确定入口文件、编译选项
       ↓
模块解析，建立 Program
       ↓
Scanner：字符 → Token
       ↓
Parser：Token → AST
       ↓
Binder：声明 → Symbol，建立作用域
       ↓
Checker：类型推导与类型检查
       ↓
Transformer：类型擦除、语法降级
       ↓
Emitter/Printer：AST → JavaScript 文本
       ↓
.js / .d.ts / .js.map
```
- TypeScript到JavaScript做erase类型擦除，这是什么？
```txt
TypeScript 编译成 JavaScript 时，大部分仅用于静态类型检查的语法会被删除，因为 JavaScript 运行时不认识这些类型信息。

会被擦除的内容包括：
- 类型标注：`const count: number = 10`
- interface 和 type 定义
- 泛型类型参数：`function identity<T>(arg: T): T`
- 类型断言：`const value = 'hello' as string`
- 类型导入：`import { type MyType } from './types'`
```

- package.json 中的 exports 有什么作用？
    - import / export 在模块组织、打包和解析中如何工作？
```txt
package.json中的exports用来声明一个npm包对外公开哪些入口，以及不同环境应该解析到哪个文件。它比main更强大，可以定义主入口、子路径入口和条件导出，还能阻止消费者直接引用包内部未公开的文件。当代码执行 import { foo } from "pkg" 时，运行时或构建工具先解析模块说明符：如果是包名，就在 node_modules 中找到该包，再读取 package.json 的 exports，根据当前条件，比如 import、require、node、browser，选择实际文件。

Node.js将exports定位为现代的包入口机制，支持多个入口、条件解析，并封装没有显示导出的内部路径。如果同时存在 main 和 exports，支持 exports 的环境会优先使用它。
- 定义主入口
- 定义子路径入口
- 封装内部实现
- 条件导出

对于ESM模块，静态的import/export 使依赖关系能在执行前确定。构建工具会据此建立模块依赖图，再进行 Tree Shaking、代码分割和打包。模块加载时则经历解析、实例化、链接和执行，导入导出之间是实时绑定，不是简单复制值。
```

```txt
自定义hook是一个以use开头的普通函数，用来抽取和复用组件中的有状态逻辑，比如状态管理、副作用、订阅、context读取或与浏览器API同步，不只是对某个原生hook的封装，而是可以组合多个原生hook、其他自定义hook、普通工具函数和外部系统操作。它复用的是逻辑，不是状态实例；同一个自定义 Hook 被两个组件调用时，两次调用的状态相互独立。

如果一个函数完全不调用任何 Hook，通常就应该写成普通函数，而不是命名为 useXxx。普通函数可以在条件、循环、事件回调和非 React 代码中调用；自定义 Hook 要遵守 Hook规则，只能在组件或其他 Hook顶层调用。

自定义hook的特殊性来自于：
- 内部可以调用React Hook
- 必须遵守Hook调用规则
- 命名约定使ESLint和React相关工具可以识别它
- 在组件渲染期间执行
- 内部原生Hook会关联到当前组件的Hook调用序列

自定义hook的作用：
- 复用有状态逻辑
- 隐藏副作用细节
- 统一资源清理
- 提升组件语义：通过hook名称表达意图
```

- MySQL 的 MVCC 是什么？事务隔离有什么要求？
```txt
MVCC是多版本并发控制，InnoDB不直接覆盖数据行，而是通过事务ID、Undo Log和Read View保存并判断不同版本的可见性，让读操作可以读取符合事务视角的历史版本。这样普通读可以不加锁，不会被写事务阻塞，从而提高读写并发能力。主要作用是保证事务隔离性的同时，减少读写之间的锁竞争，提高数据库并发性能。

事务隔离的核心要求是：多个事务并发执行时，一个事务的中间状态不能被其他事务随意看到，同时执行结果要尽可能接近串行执行。
具体需要防止产生的问题是：
- 脏读：读到其他事务尚未提交的事务
- 不可重复读：统一事务两次读取同一数据时，结果不同
- 幻读：同一事务两次按相同条件查询时，结果集的行数发生变化
- 丢失更新：两个事务同时修改数据，其中一个事务的更新被覆盖

另外在实际实践上：
- 事务尽量短，及时提交或回滚
- 事务中的查询和更新应使用合适索引，避免扩大锁范围
- 需要修改后续数据时使用`SELECT ... FOR UPDATE`，不能只依赖普通快照读
- 计数等操作应使用原子更新语句比如`SET count = count + 1`，避免先读后写的非原子操作
- 对并发覆盖问题可使用版本号实现乐观锁。
- 隔离级别不是越高越好，需要在一致性、吞吐量和锁竞争之间权衡。
```
- 什么情况下应该建索引，什么情况下不适合建索引？
```txt
索引本质上是以空间换时间，用额外的存储空间和写入成本来换取更快的查询速度。

适合建立索引的情况：
- 经常出现在WHERE查询条件中的列
- 经常用于表连接的列
- 经常用于排序或分组的列
- 区分度高的列（重复值少、唯一值）
- 经常查询固定组合条件的列
- 可形成覆盖索引的查询
- 用于保证唯一性的字段

不适合建立索引的情况：
- 数据量很小的表：全表扫描比索引查找更快
- 很少出现在查询条件中的列：索引维护成本高，查询优化效果小
- 频繁更新的列
- 区分度低的列
```
- 什么是事务？如何发起和管理一次数据库事务？
```txt
事务时数据库中的一组操作，这些操作要么全部成功提交，要么全部失败回滚，是一个不可分割的执行单元。

事务具有ACID特性：
- 原子性（Atomicity）：事务中的所有操作要么全部成功，要么全部失败回滚
- 一致性（Consistency）：事务前后数据满足业务约束
- 隔离性（Isolation）：并发事务之间互不干扰，事务的中间状态对其他事务不可见
- 持久性（Durability）：事务一旦提交，数据修改永久保存，即使系统崩溃也不会丢失

通过SQL发起事务有两种方式：
- START TRANSACTION (-> SAVEPOINT) -> COMMIT / ROLLBACK (/ ROLLBACK TO SAVEPOINT)
- BEGIN (-> SAVEPOINT) -> COMMIT / ROLLBACK (/ ROLLBACK TO SAVEPOINT)

或者是通过Prisma这样的ORM工具来发起事务：
prisma.$transaction()
```

```txt
JavaScript的单线程，是指在同一个JS执行环境下，JavaScript代码通常只有一个调用栈，同一时刻只能执行一段JS。异步操作并不是JS线程一直等待，而是交给运行环境处理。

宏任务、微任务的执行顺序：
1. 取出一个 task 执行
2. 执行过程中产生的同步代码全部完成
3. 清空整个微任务队列
4. 浏览器可能进行样式计算、布局和渲染
5. 再取出下一个 task

更详细的拆解是：
- JavaScript 引擎，例如 V8，负责解析和执行 JS、维护调用栈、执行 Promise Job 等。
- 浏览器负责定时器、网络、DOM 事件、渲染和事件循环调度。
- 浏览器与 JS 引擎共同完成微任务的入队和执行。
- HTML Standard 规定浏览器事件循环、任务、微任务检查点以及渲染的大致规则。
- ECMAScript 规范定义 Promise Job 等语言层机制，但由宿主环境提供调度和队列能力。
```

- 了解 Generator / Async Generator 吗？
    - 解决什么问题？
    - yield 之后的执行是立即发生还是进入队列？
```txt
Generator 是一种可以暂停和恢复执行的函数，使用yield暂停，使用next恢复。调用Generator函数不会立即执行，而是返回一个迭代器对象，可以通过迭代器的next方法逐步执行函数体。Generator主要用于实现惰性计算、异步流程控制和自定义迭代器。主要解决：
- 按需产生数据，避免一次性创建全部结果
- 表达可暂停、可恢复的计算过程
- 实现自定义迭代器
- 处理无限序列
- 通过外部代码控制执行步骤

普通 Generator 不依赖事件循环，也不会自动进入宏任务或微任务队列。执行到yield时，函数立即暂停，返回yield的值给调用者。调用next()时，Generator函数立即恢复执行，继续运行到下一个yield或return。
如果是在计时器中调用next()，恢复执行才会发生在对应任务中，但这是因为计时器进入了宏任务队列，而不是Generator本身的行为。

异步迭代器Async Generator通常使用fow await ... of语法来消费，它的作用是：
- 分页接口逐页获取
- 流式响应
- 文件或网络数据流
- 消息队列
- 数据到达一部分就处理一部分
- 需要异步背压的生产者/消费者模型：生产者产生数据太快、消费者处理不过来时，消费者能够反过来限制生产速度，防止任务无限堆积。

Async Generator的next()返回一个Promise，必须用await或then来异步等待结果。yield后立即返回一个Promise，异步操作完成后才会继续执行。Async Generator仍然会暂停，不会自行继续执行。只有下一次调用 next() 才会恢复。
```

- 什么是装饰器模式？
    - 从技术原理上看，它有哪些不变部分、哪些可扩展 / 可变化部分？
```txt
装饰器模式是一种结构型设计模式，在不修改原对象代码、也不通过大量子类继承的情况下，用包装的方式动态增加功能。

装饰器模式主要依靠三个机制：
1. 相同接口：原对象和装饰器是对用一个interface的implements，所以对于调用者来说可以相互替换。
2. 对象组合：装饰器内部持有另一个接口类型的对象引用，调用时可以委托给被装饰对象。这是一种组合关系，而不是继承原实现
3. 委托调用：装饰器完成增强逻辑后，把核心工作交给被包装对象。增强逻辑既可以发生在调用前，也可以发生在调用后

装饰器中稳定的部分：
- 组件对外暴露的接口
- 装饰器持有被装饰对象的结构
- 装饰器最终会把核心操作委托给被包装对象
- 调用方仍然通过统一接口使用对象
- 装饰器可以继续被其他装饰器包装

装饰器可扩展、可变化的部分：
- 调用前做什么
- 调用后做什么
- 是否调用原对象
- 是否修改参数
- 是否修改返回值
- 异常如何处理
- 多个装饰器以什么顺序组合
```
