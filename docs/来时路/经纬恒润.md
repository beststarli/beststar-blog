- 提到 Spec Coding，它在项目中是怎么使用的？对应哪一个项目？
```txt
Spec Coding是把规范作为AI编码过程中的主要上下文和事实来源，开发者先明确需求、边界、技术方案、任务拆分和验收标准，然后让agent分阶段实现，每一步追溯到对应需求。

典型流程是：
先定义需求和非目标，再澄清歧义，形成技术设计，拆分可执行任务，然后逐项编码、测试、验收，如果实现中发现规格有问题，应该先更新规格，再同步调整代码。

与Vibe Coding相比：
Vibe Coding更像是通过自然语言和AI快速结对编程：先描述想法，让AI生成代码，运行后根据效果不断修改。这样做启动快、反馈直接，很适合Demo、小工具和探索性需求，但是需求目标和决策结果容易散落在对话记录和代码中。

Spec Coding的工作范式：
1. 定义项目原则
2. 编写需求规格
3. 澄清歧义
4. 形成技术设计
5. 拆分任务
6. 实现与持续验证
7. 保持规格与代码同步

其实不是 Spec Coding 或 Vibe Coding 二选一，而是根据任务的不确定性和风险选择比例。探索阶段允许快速 Vibe，工程化交付阶段通过 Spec 固化需求、设计和验收标准。可以概括为：先 Vibe 验证方向，再用 Spec 控制交付。
```
- 是否使用过Spec工具比如OpenSpec
```txt
OpenSpec本质上是将一套用于Spec Coding工作流范式的skill通过npm下载到项目本地，然后在初始化中对应的agent调用这些skill进行开发工作。

使用步骤可以是：
1. $openspec-explore：探索方案，在需求没有完全想清楚时
2. $openspec-propose：创建方案，在明确要做什么时
3. 修改和完善规格：直接告诉agent对openspec提案进行修改，openspec提案是markdown文档，关键要写清楚requirement以及Scenario下的when/then。
4. $openspec-apply：实现，确认提案后可以调用这个skill；或者直接自然语言告诉agent按照提案完成实现和测试。
5. $openspec-verify：验证，在功能实现后调用这个skill进行验收测试，或者直接自然语言告诉agent按照提案进行验收。
6. $openspec-archive：归档，功能完成并确认后，调用这个skill将本次change保存到历史目录，并将最终需求合并进当前有效的 openspec/specs/。

完整流程：
explore → propose → 审核规格 → apply → verify → archive

在面对大型业务时，对于不同的交付功能，拆解为一一对应的change，每个change独立进行探索、设计、修改、实现、验证、归档。
- spec是系统当前已经承诺实现的行为
- change是某次即将实施的增量变化
```

```txt
这是四条不同类型的Agentic Workflow，他们共享一套Agent Runtime，这四条工作流分别是：
- 内容生成
- 提示词生成
- 内容审核
- 合规改写

这四个工作流使用同一个WorkflowRunner来管理Run、Step、Event和状态变化，但是每条Workflow有自己的输入、步骤和输出。在真实业务上，内容审核与合规改写两条工作流首尾衔接。

之所以说是Agentic Workflow，在于他的能力介于“普通业务流程”和“完全自由Agent”之间，这条Workflow在固定环节加入了LLM能力，它具有一定的agent特征：
- 有独立运行状态 AgentState；
- 有任务目标；
- 能调用模型；
- 能使用政策检索 Tool；
- 有多步骤执行轨迹；
- 能根据审核结果产生不同业务结果；
- 能暂停等待用户；
- 能生成后续改写建议；
- 执行过程可以持久化和追踪。

但又不是完全自主规划的agent：
- 步骤顺序由代码规定；
- LLM 不能任意选择工具；
- LLM 不能改变核心审核路径；
- LLM 不能绕开确定性规则；
- LLM 不能直接发布内容；
- 当前没有开放式 ReAct 循环。

是受控的Agentic Workflow，不是典型的ReAct那种Tool-calling Agent。为什么不做成一个自由Agent的原因如下：
1. 审核内容不能被模型自由跳过
2. 审核需要可预测和可审计
3. LLM不能成为最终安全边界
4. 需要控制延迟和成本
5. 文章内容本身是不可信输入
6. 发布和版本更新需要确定性事务

如果对这个系统改造，其实更应该做成一个受控的多agent系统，为每个工作流设计对应的agent，然后由统一调度器来负责流程和状态管理。这样可以在保证安全和可控的前提下，充分利用agent的灵活性和智能化。
```

- 你提到 WebSocket 是双工通信；那 HTTP 是怎样的通信模型，与 WebSocket 有什么区别？
```txt
HTTP通常是客户端发起请求，服务端返回响应的“请求-响应”模型，服务端不能在没有请求的情况下，通过普通的HTTP/1.1主动向客户端发送独立业务消息，哪怕是HTTP/2也只是做了服务端预取，而且目前已被废除。HTTP时客户端驱动的半双工式请求-响应模型。每次请求都需要携带完整的HTTP头部，增加了通信开销。它可以传输文本、图片、音频、视频等多种类型的数据，但不适合实时性要求高的场景。

WebSocket则是通过一次HTTP握手后升级为WebSocket协议，建立一个持久化的双向通信通道，客户端和服务端都可以主动发送消息，实现真正的双工通信。每条消息也无需携带完整的HTTP头部，减少了通信开销。它适合传输文本和二进制数据，尤其适合实时性要求高的场景，例如在线聊天、游戏、股票行情等。
```

- 如果要把一个数据量较大的平台设计成 Agent，让它扫描、查询和分析大量数据，你会如何设计？
```txt
不能让大模型直接扫描全部数据，而是把大模型定位为任务规划和工具编排层，把真正的数据查询、聚合和计算交给数据库、搜索引擎以及计算服务。

整体上我会设计成“规划—检索—计算—校验—呈现”的链路。用户提出自然语言问题后，Agent 先识别意图，将复杂任务拆成若干步骤，例如确定数据范围、检索相关数据、执行统计分析、验证结果，最后生成结论。

数据层需要根据类型选择不同的存储和索引方案：结构化数据进入关系数据库或分析型数据库，文本资料进入全文检索和向量索引，时空数据使用空间数据库或专门的时空索引，图片、日志等大对象放在对象存储。Agent 不能直接拥有任意查询权限，而是通过经过约束的工具调用这些系统。

如果是扫描和分析海量数据，我会优先把计算下推到数据端，比如使用分页、条件过滤、字段裁剪、聚合查询和分区计算，只把统计结果或少量高相关样本返回给大模型。对于耗时任务，会转换成异步作业，通过任务队列执行，并把进度、中间结果和最终结果以事件流方式反馈给前端。

在准确性方面，最终答案必须携带数据来源、查询条件、时间范围和计算口径。涉及数值统计时，应由确定性程序计算，而不是让模型心算；还可以增加结果校验节点，例如检查 SQL 合法性、数据权限、异常值和结果一致性。

前端方面，我会把 Agent 的运行过程做成可观察的状态机，展示当前处于规划、查询、分析还是生成阶段，同时支持取消、重试、修改条件和查看数据来源。大量结果不会全部渲染，而会采用虚拟列表、分页、渐进加载和图表抽样。

最后还要重点考虑权限、成本和可恢复性，包括行列级权限、敏感信息脱敏、工具白名单、Token 和查询成本限制、超时重试、幂等以及人工确认机制。上线前先从只读的低风险分析场景开始，再逐步开放写操作。
```

```txt
真正困难的不是 JSX 改成 Vue Template，而是组件模型、状态管理、路由、生态依赖和团队工程体系的迁移。首先盘点项目规模和依赖，包括页面数量、公共组件、状态管理、路由、表单、图表、富文本编辑器以及一些只支持 React 的第三方库，区分哪些代码可以复用，哪些必须重写。纯 TypeScript 工具函数、接口类型、请求层和业务规则一般可以保留，但视图组件和框架绑定较深的 Hooks 通常需要重构。

在组件层，需要把 React 的 props、state、Hooks、Context、JSX 和生命周期，映射到 Vue 3 的 props、ref/reactive、computed、watch、provide/inject、模板以及 Composition API。这里不能机械地把 useEffect 全部改成 watch，而要重新区分派生状态、业务副作用和组件生命周期，否则容易造成重复请求、响应式失效或内存泄漏。

工程层还要迁移 React Router、Redux 或 Zustand 等能力，例如换成 Vue Router 和 Pinia，同时重新处理路由守卫、权限、状态持久化、SSR、按需加载和构建配置。测试也需要调整，端到端测试如果基于 Playwright，复用程度会高一些。

实施上我更倾向于渐进式迁移，而不是一次性重写。可以先抽离与框架无关的业务层和 API 层，再建立 Vue 项目的基础设施和组件规范，随后按业务模块迁移，通过微前端、独立路由或新旧应用并行运行来控制风险。每迁移一个模块，都做视觉回归、功能回归和性能对比。

主要风险包括功能回归、第三方库缺少 Vue 替代方案、状态和生命周期语义差异、样式变化、性能退化、测试覆盖不足，以及团队同时维护两套技术栈造成的成本。
```
